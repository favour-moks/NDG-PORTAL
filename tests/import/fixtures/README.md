# Import fixtures

**These are synthetic.** The roadmap (`docs/product-roadmap.md`, TASK-019) calls for testing
against the real `Edo Coaches Payment Report.xlsx` — 45 rows, two payment batches, 16
leading-zero accounts, 11 bank name variants, mixed name casing. That file wasn't available
when Phase 1 was built, and it would have contained real people's BVN/NIN and bank account
details — not something to fabricate and pass off as real. These fixtures reproduce the
documented *structural* quirks with fictional names, banks, and account numbers, generated by
`generate.mjs`. Swap in the real file later by replacing `edo-coaches-real.xlsx` — the pipeline
doesn't care that this one is synthetic.

Regenerate with:

```bash
node tests/import/fixtures/generate.mjs
```

## What each file proves

**`edo-coaches-real.xlsx`** — the fixture of record. 45 rows, all valid: every row has a
resolvable bank, a valid 10-digit account number, and at least one of BVN/NIN. Covers all 11
seeded bank spellings (GTBANK, STANBIC IBTC BANK, UNITED BANK FOR AFRICA, FIRST BANK, FCMB,
Polaris Bank, ZENITH BANK, STERLING BANK, WEMA BANK, FIDELITY BANK, ECOBANK), 16 rows with
leading-zero account numbers stored as text, and 16 rows with ALL CAPS names in shuffled word
order (to exercise name normalisation). Four of the rows are Fidelity Bank accounts sharing the
same first five digits, two of which differ only in their final three digits — genuinely
different people, included specifically to prove the dedup pass never fuzzy-matches account
numbers, only names. If this file round-trips (45 accepted, 0 rejected), the import is right.

**`edo-coaches-zeros-destroyed.xlsx`** — the same 45 rows, except every account number cell is
stored as an Excel *number* instead of text, so every leading zero is already gone by the time
the file is opened. Proves the validator rejects the resulting short numbers with a message that
names the digit count and explains why (leading zeros lost when Excel stores a number) — and
proves it never tries to pad the number back to 10 digits, which could pay the wrong person.

**`wrong-template.xlsx`** — three unrelated columns, none of the six the import template
requires. Proves the parser rejects the file before attempting to read any row data, naming
exactly which required columns are missing.

Covered by `fixtures.test.ts` in this directory, which runs the real `parseSpreadsheet` /
`validateRow` pipeline against all three files and asserts on the outcomes above.
